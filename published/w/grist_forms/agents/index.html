Form Builder

Pour un agent

Compose un formulaire Grist, le relie à sa table, le publie dans le document et relit les réponses. Ces commandes ne font que lire et calculer : elles rendent des plans, elles n’écrivent rien dans un document. Cette page est écrite à partir de la fiche de capacités du widget : elle ne peut pas dire autre chose que ce qu’il sait faire (version 1.7.1).

Ce qu’un agent peut faire

Chaque commande reçoit une entrée au format JSON et rend une sortie au format JSON. Les commandes ci-dessous sont celles que ce widget propose aujourd’hui.

CommandeVerbeCe qu’elle fait
forms_capacitesPrésenterPrésente Form Builder : ce qu’il sait faire (les commandes par verbe), ce qu’il ne couvre pas encore, les contrats qu’il produit et lit, ses limites. À appeler en premier.
forms_plan_schemaConfigurerCalcule le plan d’actions Grist qui crée la table et les colonnes manquantes d’un FormDef. Il ne lit AUCUN document : il compare le FormDef à colonnes_existantes et table_existe, que l’appelant doit fournir. Sans eux, il suppose une table sans colonne et prévoit un AddColumn par champ, sans AddTable. Il rend le plan sans l’appliquer ; il ne change jamais le type d’une colonne existante. Il refuse (ok: false, errors) un Choice ou ChoiceList sans liste de choix (dans choices[colId] à la racine ou options.choices du champ).
forms_formdef_depuis_colonnesCréerDéduit un FormDef des colonnes d’une table Grist (une question par colonne, hors colonnes internes et colonnes calculées). Rend formdef: null quand aucune colonne ne donne de question. Les choix d’une colonne Choice ou ChoiceList sont lus dans son widgetOptions (chaîne JSON {"choices":["a","b"]}) et rangés dans options.choices du champ ; sans widgetOptions, le champ n’a pas de choix et forms_plan_schema le refusera. La racine choices du FormDef rendu reste {} : les choix vivent dans le champ.
forms_formdef_depuis_formulaire_gristCréerLit les formulaires natifs d’un document Grist et rend chacun en FormDef. L’entrée est le contenu des tables de métadonnées (tables, colonnes, vues, sections, champs), tel que fetchTable le rend.
forms_valider_formdefStructurerContrôle un FormDef contre son contrat (formdef-1.0) et rend les écarts. conforme ne dit QUE le respect du contrat : il ne garantit pas que forms_plan_schema produira un plan. plan_realisable dit si le plan serait calculé sur une table à créer, et avertissements rend les motifs de refus du plan (par exemple « choices manquants » pour un Choice sans choix). Un FormDef conforme rend une liste d’écarts vide.
forms_valider_conditionStructurerContrôle une condition d’affichage (grammaire conditions-1.0). Rend les erreurs avec leur chemin ; bloquant dit si la condition serait refusée. Un opérateur inconnu est une faute, jamais « vrai ».
forms_verifier_formatStructurerÉprouve une valeur contre un format nommé (iban, siren, siret, codePostal, insee, heure, courriel, nom, prenom, nomComplet, telephone) et rend la forme normalisée. Un format inconnu laisse tout passer et le dit (connu: false). message_si_invalide est le message à montrer si la valeur est invalide, pas un verdict : le verdict est valide. Pour attacher un format à une question d’un FormDef, ajouter au champ validation: { "format": "courriel" } (mode verifier par défaut : une réponse non conforme est refusée ; corriger remet la forme en ordre sans refuser, réservé aux noms).
forms_formdef_vers_manifeste_enqueteStructurerConvertit un FormDef en manifeste d’enquête (survey-manifest). Sens inverse : forms_manifeste_enquete_vers_formdef.
forms_manifeste_enquete_vers_formdefStructurerConvertit un manifeste d’enquête en FormDef. Sens inverse : forms_formdef_vers_manifeste_enquete.
forms_resoudre_themePersonnaliserDérive les variables de thème (--kit-*) d’un ThemeDef 1.0 à partir de ses couleurs de départ, pour un mode clair ou sombre. Un thème illisible est refusé en entier.
forms_plan_publicationPublierCalcule les actions qui créent une page personnalisée liée à une table, et les options de la vue qui porte le formulaire (HTML et JS déjà assemblés). Il rend le plan sans l’appliquer.
forms_syntheseTraiterRelit les réponses d’un formulaire avec le FormDef qui les a produites : fréquences, échelles, classements, listes. La table seule n’est pas lisible, le FormDef sait ce que chaque colonne veut dire.

Ce qui n’est pas encore couvert

Ces verbes n’ont aucune commande : un agent ne peut pas encore les accomplir par ce moyen.

  • Modifier
  • Exploiter
  • Récolter

Ce que les commandes lisent et produisent

Un contrat est un format partagé : ce que l’un écrit, l’autre le lit sans avoir à le connaître.

  • Produit : FormDef 1.0 — au catalogue des contrats du dépôt
  • Produit : Conditions 1.0 — au catalogue des contrats du dépôt
  • Produit : Survey Manifest 1 — hors catalogue, empreinte sha256:147c959fee0b3b6e
  • Lu : FormDef 1.0 — au catalogue des contrats du dépôt
  • Lu : Conditions 1.0 — au catalogue des contrats du dépôt

forms_formdef_depuis_colonnes

Déduit un FormDef des colonnes d’une table Grist (une question par colonne, hors colonnes internes et colonnes calculées). Rend formdef: null quand aucune colonne ne donne de question. Les choix d’une colonne Choice ou ChoiceList sont lus dans son widgetOptions (chaîne JSON {"choices":["a","b"]}) et rangés dans options.choices du champ ; sans widgetOptions, le champ n’a pas de choix et forms_plan_schema le refusera. La racine choices du FormDef rendu reste {} : les choix vivent dans le champ.

N’écrit rien.

Exemple : Une table de deux colonnes
// entrée
{
  "tableId": "Inscriptions",
  "colonnes": [
    {
      "colId": "nom",
      "type": "Text",
      "label": "Nom"
    },
    {
      "colId": "age",
      "type": "Int",
      "label": "Âge"
    }
  ]
}

// sortie
{
  "formdef": {
    "manifest_version": "1.0.0",
    "id": "derive:Inscriptions",
    "title": "Inscriptions",
    "description": "",
    "tableId": "Inscriptions",
    "composeMode": "bind",
    "sections": [
      {
        "id": "main",
        "label": "Inscriptions",
        "fields": [
          {
            "colId": "nom",
            "label": "Nom",
            "type": "Text",
            "widget": "text",
            "required": false
          },
          {
            "colId": "age",
            "label": "Âge",
            "type": "Int",
            "widget": "number",
            "required": false
          }
        ]
      }
    ],
    "choices": {}
  }
}

forms_formdef_depuis_formulaire_grist

Lit les formulaires natifs d’un document Grist et rend chacun en FormDef. L’entrée est le contenu des tables de métadonnées (tables, colonnes, vues, sections, champs), tel que fetchTable le rend.

N’écrit rien.

Exemple : Un document sans formulaire natif
// entrée
{
  "meta": {}
}

// sortie
{
  "formulaires": []
}

forms_valider_formdef

Contrôle un FormDef contre son contrat (formdef-1.0) et rend les écarts. conforme ne dit QUE le respect du contrat : il ne garantit pas que forms_plan_schema produira un plan. plan_realisable dit si le plan serait calculé sur une table à créer, et avertissements rend les motifs de refus du plan (par exemple « choices manquants » pour un Choice sans choix). Un FormDef conforme rend une liste d’écarts vide.

N’écrit rien.

Exemple : Un FormDef vide
// entrée
{
  "formdef": {}
}

// sortie
{
  "conforme": false,
  "ecarts": [
    "(racine) : propriété requise absente : manifest_version",
    "(racine) : propriété requise absente : id",
    "(racine) : propriété requise absente : title",
    "(racine) : propriété requise absente : tableId",
    "(racine) : propriété requise absente : composeMode",
    "(racine) : propriété requise absente : sections",
    "(racine) : propriété requise absente : choices"
  ],
  "plan_realisable": false,
  "avertissements": []
}

forms_valider_condition

Contrôle une condition d’affichage (grammaire conditions-1.0). Rend les erreurs avec leur chemin ; bloquant dit si la condition serait refusée. Un opérateur inconnu est une faute, jamais « vrai ».

N’écrit rien.

Exemple : Une règle correcte
// entrée
{
  "condition": {
    "field": "age",
    "operator": ">=",
    "value": 18
  }
}

// sortie
{
  "valide": true,
  "erreurs": []
}

forms_verifier_format

Éprouve une valeur contre un format nommé (iban, siren, siret, codePostal, insee, heure, courriel, nom, prenom, nomComplet, telephone) et rend la forme normalisée. Un format inconnu laisse tout passer et le dit (connu: false). message_si_invalide est le message à montrer si la valeur est invalide, pas un verdict : le verdict est valide. Pour attacher un format à une question d’un FormDef, ajouter au champ validation: { "format": "courriel" } (mode verifier par défaut : une réponse non conforme est refusée ; corriger remet la forme en ordre sans refuser, réservé aux noms).

N’écrit rien.

Exemple : Un code postal
// entrée
{
  "format": "codePostal",
  "valeur": "13001"
}

// sortie
{
  "connu": true,
  "valide": true,
  "normalise": "13001",
  "message_si_invalide": "Ce n’est pas un code postal (5 chiffres)."
}

forms_plan_schema

Calcule le plan d’actions Grist qui crée la table et les colonnes manquantes d’un FormDef. Il ne lit AUCUN document : il compare le FormDef à colonnes_existantes et table_existe, que l’appelant doit fournir. Sans eux, il suppose une table sans colonne et prévoit un AddColumn par champ, sans AddTable. Il rend le plan sans l’appliquer ; il ne change jamais le type d’une colonne existante. Il refuse (ok: false, errors) un Choice ou ChoiceList sans liste de choix (dans choices[colId] à la racine ou options.choices du champ).

N’écrit rien.

Exemple : Une table absente
// entrée
{
  "formdef": {
    "manifest_version": "1.0.0",
    "id": "exemple",
    "title": "Exemple",
    "tableId": "Exemple",
    "composeMode": "bind",
    "sections": [
      {
        "id": "main",
        "label": "Exemple",
        "fields": [
          {
            "id": "nom",
            "colId": "nom",
            "type": "Text",
            "label": "Nom"
          }
        ]
      }
    ],
    "choices": {}
  },
  "colonnes_existantes": [],
  "table_existe": false
}

// sortie
{
  "ok": true,
  "errors": [],
  "actions": [
    [
      "AddTable",
      "Exemple",
      [
        {
          "id": "nom",
          "type": "Text",
          "label": "Nom",
          "isFormula": false
        }
      ]
    ]
  ]
}

Limites

  • Version 1 en lecture seule : aucune commande n’écrit dans un document Grist.
  • Appliquer un plan de schéma ou de publication n’est pas encore une commande.
  • Le formulaire vivant (rendu, saisie, envoi) ne se pilote pas par ces commandes : il vit dans une page.
  • Les commandes ne se connectent à aucun document : les tables et les réponses sont données en entrée.
